# Issue 32 — Orca focus investigation

## Environment and scope

Investigated [#32](https://github.com/stevdrey/fx-atspi-bridge/issues/32) on baseline `5bcfb4b01701725fca7ef313437fe2782889ab2a` and the local source changes described here. Fedora 44, kernel 7.2.13-200.fc44.x86_64, GNOME Shell 50.6 and Mutter 50.6, Wayland session, Zulu JDK 27+35, JavaFX 27, Orca 50.3, at-spi2-core 2.60.7 and PyGObject 3.56.3. This investigation did not independently re-establish the JavaFX window backend.

## Findings and correction

The user reported that Orca still announced only pressed keys on the baseline. An independent libatspi listener associated control focus events with `JavaFX AT-SPI Lab` and window activation events with a second `java` provider from the same process. While the window was focused and showing, an independent state query found the latter frame active but the bridge frame not active. Orca 50.3's `can_be_active_window` rejects a frame without ACTIVE, and its focus handler checks that condition. This establishes a concrete incompatibility; the GObject startup warning has not been linked to it.

The bridge now derives ACTIVE for showing, focused frames and emits `object:state-changed:active` when that state changes. Unit tests cover activation, deactivation, hiding, removal and exclusion of ordinary controls. An independent libatspi state query against the corrected laboratory observed its showing, focused frame as active. In assisted post-change listening, the user reported that Orca now names controls on Tab, explicitly including Limpiar, but also speaks additional material the user could not identify. The user’s subsequent transcription included fragments matching the fixed provider description. Orca can speak accessible descriptions, and the bridge supplied that provider identifier as every object’s description and help text. Both are now empty rather than describing each control with provider metadata; a post-change libatspi query confirmed empty descriptions for Entrada, Agregar and Limpiar. On the version with both corrections, the user reported that Orca announces control names and no longer repeats “Experimental JavaFX”. Individual results for Entrada and Agregar, role announcements, reverse navigation, edited text and button outcomes remain unverified. A PID- and application-identified libatspi listener subsequently observed the bridge frame emit ACTIVE false and true when the window lost and regained focus, and focus transitions for Entrada and Limpiar.

## Verification

- `GRADLE_USER_HOME=<temporary-cache> ./gradlew check :examples:fx-lab:installDist --offline --no-daemon`: **Passed**, 290 Java tests, zero failures, errors or skips; both consumer integration checks passed. The build printed Javadoc warnings and a GLib invalid-signal diagnostic during tests. The initial restricted wrapper invocation could not write its lock, and the temporary-cache attempt could not determine a wildcard IP; the successful command ran outside the sandbox.
- Baseline libatspi query found Entrada as an entry and Agregar and Limpiar as buttons, all focusable. The historical assisted smoke failed; the user reconfirmed only key echo on this baseline. No result is inferred for edited text or button outcomes.
- Post-change assisted Orca listening: control names are now heard, including Limpiar; after removal of the fixed provider description, the user reported that “Experimental JavaFX” is no longer repeated. This is a partial smoke result, not full interoperability. A working-reference comparison and additional platforms remain unverified. No native-Wayland or general screen-reader compatibility claim is made. Raw traces are not committed.
